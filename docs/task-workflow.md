# 비개발 업무 흐름 (task workflow)

개발 흐름(devflow)을 코드가 아닌 일에 그대로 옮긴 것이다. 일 자체를 하네스로 만들지 않는다. devflow는 일이 끊기지 않게 하는 배관만 맡고, 일을 어떻게 할지는 맡은 봇(관리 세션)과 작업자가 판단한다.

## 한눈에

```
[일이 생김]                 크론 시각 · 준의 말 · 다른 봇의 요청 · 새 메시지
     │
     ▼
[작업 정의]  dv submit --kind task      브리프 1장: 목표 / 근거로 쓸 자료 / 결과물 / 끝 조건 / 보낼 곳
     │                                  (= 이슈. 저장소 이슈 또는 브리프 파일)
     ▼
[배정]       입찰 → 기기 · 작업자        Codex / Claude Code / omp / Hermes 세션 중 하나
     │
     ▼
[작업]       격리된 작업 폴더에서        읽기는 원본, 쓰기는 out/ 에만
     │       결과물 out/ + report.md     (출처, 확인한 것, 못 한 것)
     ▼
[완료]       dv done                    out/ 을 그 순간 그대로 고정(스냅숏)
     │
     ▼
[확인]       담당 봇 관리 세션           브리프의 끝 조건과 결과물 대조
     │       맞으면 → 전달 / 모자라면 → dv send 로 한 번 되돌림
     ▼
[전달]       dv land                    Desk 등 목적지에 새 이름으로 복사(덮어쓰지 않음)
     │                                  준에게 보낼 것이면 한두 줄 + 파일
     ▼
[기록]       작업 기록 · Honcho         누가 무엇을 근거로 했는지 남김(말한 쪽은 들어온 경로로)
```

멈춤·죽음 감지, 같은 자리 되살리기, 자리 입찰, 이벤트 묶음 처리는 개발 흐름과 같은 것을 쓴다.

## 개발 흐름과의 대응

| 개발 | 비개발 |
| --- | --- |
| GitHub 이슈 | 작업 브리프 (이슈 또는 파일) |
| 작업 브랜치 · worktree | 격리 작업 폴더 + `out/` |
| PR | `out/` + `report.md` |
| CI · 봇 리뷰 | 끝 조건 대조 (형식 검사가 있으면 스크립트로) |
| merge | `dv land` = 목적지로 복사·전송 |
| 머지 뒤 실사용 QA | 받은 사람 반응 · 다음 회차에서 빠진 것 점검 |

## 첫 적용 대상 (지금 대화 세션 안에서 직접 하는 반복 업무)

| 봇 | 일 | 주기 | 결과물 | 전달 |
| --- | --- | --- | --- | --- |
| 리나 | 아침 브리핑 | 매일 09:00 | 브리핑 본문 | 준 텔레그램 |
| 리나 | 저녁 완료 확인 | 매일 21:00 | 확인 목록 | 준 텔레그램 |
| 리나 | 주간 점검 | 일 20:00 | 점검 문서 | Desk + 준 |
| 리나 | 카톡·Discord 업무 할 일 | 매일 08:30 | 할 일 목록 | Todoist + 준 |
| 리나 | 카톡 인물 동향 → 루미 | 매일 08:50 | 동향 파일 | 루미 |
| 리나 | 새 메시지 알림·Todoist 정리 | 10분 | 알림 · 할 일 | 준 · Todoist |
| 리나 | 일회성 확인 (소송·실적) | 지정 시각 | 확인 보고 | 준 |
| 루미 | 인물위키 카톡 보강 | 매일 23:30 | 위키 수정안 | Desk 위키 |
| 아린 | 식사 기록 정리 | 매일 23:30 | 정리 기록 | Desk |
| 아린 | 인바디·몸무게 알림 | 매일 23:00 | 알림 | 준 텔레그램 |

10분 주기 알림처럼 짧고 잦은 일은 작업자를 따로 띄우지 않고 지금처럼 바로 처리한다. 여기에는 "끝났는지 확인하고 기록" 단계만 붙인다. 브리핑·점검·위키 보강처럼 결과물이 있는 일부터 이 흐름으로 옮긴다.

## 옮기는 순서

1. devflow 작업 종류 `task` (devflow#101, PR #107) 합치기: 격리 폴더, `out/`, 스냅숏, 대조 뒤 전달.
2. 리나 **주간 점검** 하나로 시험: 크론이 직접 쓰던 것을 `dv submit --kind task`로 바꾸고, 리나 관리 세션이 끝 조건 대조 후 전달. 한 주 돌려 보고 빠진 것을 고친다.
3. 리나 아침 브리핑·저녁 확인, 루미 위키 보강으로 넓힌다.
4. 쓰면서 고친 것은 리나 작업 엔진 기능으로 옮긴다 (devflow는 시험장).

## 하지 않는 것

- 일의 내용을 규칙으로 정하지 않는다. 브리프는 목표와 끝 조건만 적는다.
- 준에게 보내는 말은 담당 봇의 말투와 기준을 그대로 쓴다. devflow가 글을 고치지 않는다.
- 원본(카톡·메일·Desk)을 작업자가 직접 고치지 않는다. 쓰기는 `out/`에만, 반영은 전달 단계에서만.
